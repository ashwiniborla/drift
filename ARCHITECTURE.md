## What is Drift?

Drift is a **workflow orchestration platform** built on top of Temporal. It provides:

- A **REST API** (`api` module) for managing workflow and node definitions, and for triggering/managing workflow runs.
- A **Temporal Worker** (`worker` module) that executes workflow logic by evaluating node graphs and making outbound HTTP activity calls.
- A **Java SDK** (`java-sdk`) that defines extension points (SPI) and model classes for consumers.
- A **shared commons library** (`commons`) that provides HBase persistence, Redis caching, Temporal interface definitions, and domain utilities.

The system is designed to be **definition-driven**: workflow behaviour is defined as DAGs of `NodeDefinition` objects stored in HBase, not in compiled Java code. The worker reads these definitions at runtime and executes them dynamically.

## Key Design Patterns

### 1. Definition-Driven Workflow Execution

Workflow graphs are stored as `NodeDefinition` records in HBase (not in code). Each node has:
- An **action type** (HTTP call, conditional, transform, etc.)
- **Input/output mappings** using Groovy/Mustache templates
- **Successor node references** forming a DAG

The worker reads these at runtime, resolves templates with the current workflow context, and makes the corresponding HTTP calls. This makes workflows configurable without redeployment.

### 2. Two-Layer Cache with Pub/Sub Invalidation

`NodeDefinition` and `WorkflowDefinition` objects are cached in-memory (Guava `LoadingCache`) backed by HBase. Both `api` and `worker` maintain their own caches.

Cache invalidation:
1. A write to HBase (via `api`) publishes an invalidation message to Redis pub/sub.
2. Both `api` and `worker` subscribe to this channel (`RedisPubSubService` / `RedisCacheInvalidator`).
3. On message receipt, both evict the stale key from their local cache.

### 3. Temporal Workflow Execution

- `api` submits workflow runs to Temporal via the Temporal client (gRPC :7233).
- `worker` polls Temporal for tasks on the configured task queue.
- `GenericWorkflowImpl` implements the Temporal workflow interface (`GenericWorkflow`).
- `WorkflowNodeExecutor` implements Temporal activities — each node execution is one activity.

### 4. SPI Extension Points (java-sdk)

Consumer applications can provide custom implementations of:
- `ABTestingProvider` — A/B testing decisions
- `TokenProvider` — auth token generation
- `SchedulerProvider` — custom task scheduling

Factory classes load implementations via `ServiceLoader` (Java SPI), falling back to no-op defaults.

## Data Stores

### HBase
- **Tables**: WorkflowHB, NodeHB, WorkflowContextHB (runtime state)
- **Access**: via DAO classes in `commons/persistence/dao/`
- **Connection**: ZooKeeper quorum configured via `hbasePropertiesPath` URL

### Redis Sentinel
- **Usage**: Cache invalidation pub/sub + optional session storage
- **Client**: Jedis with Sentinel mode
- **Config**: `master`, `sentinels`, `password`, `prefix` from environment variables

### Temporal (PostgreSQL-backed)
- **Temporal Server**: Running in Rancher Desktop with PostgreSQL backend
- **Client**: Temporal Java SDK (gRPC transport to :7233)
- **Namespace**: default (configurable via `TEMPORAL_TASK_QUEUE`)
