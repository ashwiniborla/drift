This page covers the design, implementation, and validation of per-node retry and timeout configuration for Drift activity execution on Temporal.

Background

Drift orchestrates workflows as DAGs on top of Temporal. Every workflow node (HTTP call, processor, etc.) is executed as a Temporal activity. Before this change, all activities shared a single global ActivityOptions object defined in OptionsStore.activityOptionsV1 — a hardcoded 10-second timeout with no retry policy.

This meant:

  • No way to retry a flaky HTTP node without wrapping it in custom code.
  • No way to give a slow node a longer timeout without affecting every other node in the system.
  • Any transient failure immediately moved the workflow to its defaultFailureNode.

Objective

Allow workflow authors to declare, per node, a custom activity timeout and retry policy — directly in the workflow definition JSON stored in HBase. No code deployment required to change retry behaviour for a workflow.

Scope

In scopeOut of scope
  • Per-node timeoutSeconds (startToCloseTimeout)
  • Per-node retryConfig (maxAttempts, initialInterval, maxInterval, backoffCoefficient)
  • Platform-level defaults via activityDefaults in worker config YAML
  • Applies to all non-local activity types (HTTP, PROCESSOR, DELEGATE, CONTEXT_OVERRIDE, etc.)
  • Local activity types (INSTRUCTION, BRANCH, GROOVY, SUCCESS, FAILURE) — these use localActivityOptions unchanged
  • Dynamic config service integration
  • Per-tenant retry defaults

Design

New DSL fields on WorkflowNode

Two optional fields added to WorkflowNode (stored in HBase as part of the workflow definition JSON):

json { "instanceName": "callExternalService", "resourceId": "my-http-node", "resourceVersion": "1", "type": "NODE", "timeoutSeconds": 30, "retryConfig": { "maxAttempts": 3, "initialIntervalSeconds": 2, "maxIntervalSeconds": 30, "backoffCoefficient": 2.0 }, "end": false }

Both fields are optional. If omitted, the platform defaults from activityDefaults in configuration.yaml are used.

Component changes

1. NodeRetryConfig (commons)

New class: commons/src/main/java/com/flipkart/drift/commons/model/node/NodeRetryConfig.java

Simple POJO deserialised from the workflow definition. Fields: maxAttempts, initialIntervalSeconds (default 1), maxIntervalSeconds (default 20), backoffCoefficient (default 2.0).

2. WorkflowNode (commons)

Modified: commons/src/main/java/com/flipkart/drift/commons/model/node/WorkflowNode.java

Two new nullable fields added:

java @JsonProperty("timeoutSeconds") private Integer timeoutSeconds; @JsonProperty("retryConfig") private NodeRetryConfig retryConfig;

3. ActivityDefaultsConfig (worker)

New class: worker/src/main/java/com/flipkart/drift/worker/config/ActivityDefaultsConfig.java

Bound to the activityDefaults YAML block. Provides platform-wide defaults when a node omits its own config.

4. ActivityOptionsBuilder (worker)

New class: worker/src/main/java/com/flipkart/drift/worker/temporal/ActivityOptionsBuilder.java

Core logic: takes a WorkflowNode and returns a fully configured Temporal ActivityOptions. Node-level values override defaults; defaults override hard-coded fallbacks.

java public ActivityOptions build(WorkflowNode node) { int timeout = node.getTimeoutSeconds() != null ? node.getTimeoutSeconds() : defaultTimeoutSeconds; int maxAttempts = retryConfig != null ? retryConfig.getMaxAttempts() : defaultMaxAttempts; // ... initialInterval, maxInterval, backoff resolved the same way return ActivityOptions.newBuilder() .setStartToCloseTimeout(Duration.ofSeconds(timeout)) .setRetryOptions(RetryOptions.newBuilder() .setMaximumAttempts(maxAttempts) .setInitialInterval(Duration.ofSeconds(initialInterval)) .setMaximumInterval(Duration.ofSeconds(maxInterval)) .setBackoffCoefficient(backoff) .build()) .build(); }

5. ActivityOptionsBuilderHolder (worker)

New class: worker/src/main/java/com/flipkart/drift/worker/temporal/ActivityOptionsBuilderHolder.java

Thread-safe singleton holder. Initialised once at worker startup. Workflow execution threads call ActivityOptionsBuilderHolder.get().build(currentNode).

6. TemporalWorkerManaged (worker)

Modified: worker/src/main/java/com/flipkart/drift/worker/bootstrap/TemporalWorkerManaged.java

Added one line to start() to initialise the holder before the worker factory starts polling:

java @Override public void start() { ActivityOptionsBuilderHolder.init(new ActivityOptionsBuilder(this.configuration.getActivityDefaults())); workerFactory.start(); }

7. WorkflowNodeExecutor (worker)

Modified: worker/src/main/java/com/flipkart/drift/worker/workflows/WorkflowNodeExecutor.java

Replaced the static global options with per-node options:

java // Before io.temporal.workflow.Workflow.newUntypedActivityStub(OptionsStore.activityOptionsV1) // After io.temporal.workflow.Workflow.newUntypedActivityStub(ActivityOptionsBuilderHolder.get().build(currentNode))

8. configuration.yaml (worker)

Modified: worker/src/main/resources/config/configuration.yaml

Added platform defaults block and fixed a YAML quoting issue with REDIS_PREFIX:

yaml # Redis prefix — quoted to prevent YAML colon parse error prefix: "${REDIS_PREFIX}" # Platform-level activity defaults (per-node overrides take priority) activityDefaults: defaultMaxAttempts: 1 defaultTimeoutSeconds: 10

How to use

Register a node definition (HTTP)

bash curl -X POST http://<drift-api>/nodeDefinition/ \ -H "Content-Type: application/json" \ -H "X_TENANT_ID: <tenant>" \ -H "X_CLIENT_ID: <client>" \ -d '{ "id": "my-http-node", "name": "My HTTP Node", "type": "HTTP", "httpComponents": { "url": {"type": "STATIC", "value": {"type": "STRING", "data": "https://example.com/api"}}, "method": "POST", "contentType": "application/json" } }'

Register a workflow with retry + timeout

bash curl -X POST http://<drift-api>/workflowDefinition/ \ -H "Content-Type: application/json" \ -H "X_TENANT_ID: <tenant>" \ -H "X_CLIENT_ID: <client>" \ -d '{ "id": "my-workflow", "startNode": "step1", "states": { "step1": { "instanceName": "step1", "resourceId": "my-http-node", "resourceVersion": "1", "type": "NODE", "timeoutSeconds": 30, "retryConfig": { "maxAttempts": 3, "initialIntervalSeconds": 2, "maxIntervalSeconds": 30, "backoffCoefficient": 2.0 }, "end": true } } }'

Publish and activate

bash # Publish node curl -X POST http://<drift-api>/nodeDefinition/my-http-node/publishNode/ \ -H "X_TENANT_ID: <tenant>" -H "X_CLIENT_ID: <client>" # Publish workflow curl -X POST http://<drift-api>/workflowDefinition/my-workflow/publishWorkflow/ \ -H "X_TENANT_ID: <tenant>" -H "X_CLIENT_ID: <client>" # Activate at version 1 curl -X POST "http://<drift-api>/workflowDefinition/my-workflow/activate?version=1" \ -H "X_TENANT_ID: <tenant>" -H "X_CLIENT_ID: <client>"

Start a workflow

bash curl -X POST http://<drift-api>/v3/workflow/start \ -H "Content-Type: application/json" \ -H "X_TENANT_ID: <tenant>" \ -H "X_CLIENT_ID: <client>" \ -d '{ "workflowId": "run-001", "params": {"workflowId": "my-workflow", "version": "1"}, "issueDetail": {"issueId": "ISSUE-123"}, "threadContext": {"tenant": "<tenant>", "clientId": "<client>"} }'

Validation

Retry scenario

Workflow drift-retry-final — node with maxAttempts: 3 hitting an endpoint that returns HTTP 500 for the first 2 calls and HTTP 200 on the 3rd.

Expected on Temporal UI: Activity callRetryEndpoint shows attempt: 3 in its last STARTED event. Final workflow status: COMPLETED.

Observed: ✅ Workflow WORKFLOW_EXECUTION_STATUS_COMPLETED, activity reached attempt 3.

Timeout scenario

Workflow drift-timeout-final — node with timeoutSeconds: 5 hitting an endpoint that sleeps for 30 seconds.

Expected on Temporal UI: ACTIVITY_TASK_TIMED_OUT with TIMEOUT_TYPE_START_TO_CLOSE after 5 seconds. Final workflow status: FAILED.

Observed: ✅ Workflow WORKFLOW_EXECUTION_STATUS_FAILED with error "Activity task timed out … RETRY_STATE_MAXIMUM_ATTEMPTS_REACHED".

Unit tests

New test class: worker/src/test/java/com/flipkart/drift/worker/temporal/ActivityOptionsBuilderTest.java

  • Node with retryConfig — verifies maxAttempts, intervals, backoff are applied
  • Node with timeoutSeconds — verifies startToCloseTimeout is set
  • Node with neither — verifies platform defaults are used
  • Null ActivityDefaultsConfig — verifies hard-coded fallbacks kick in
